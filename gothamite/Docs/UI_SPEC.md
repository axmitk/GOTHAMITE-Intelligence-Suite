# UI_SPEC.md

**Repo:** `GOTHAMITE`
**Scope:** `frontend-react/` only. Backend is untouched and already working — do not modify anything under `backend/`.
**Prerequisites:** `docs/MASTER_CONTEXT.md`, `docs/SECURITY.md` (language rules), `docs/DATA_MODEL.md`

This is a visual design spec: layout, color, typography, per-screen composition. `UX_SPEC.md` covers interaction and state. `MIGRATION_PLAN.md` covers build phases.

---

## 1. Direction

An analyst intelligence tool, not a consumer app. Dense, legible, dark. The reference points are Maltego, Palantir Gotham, and general SOC/SIEM dashboards — not a SaaS landing page. Judges should feel like they're looking at something an analyst would actually use, not a demo skin.

**The single visual job of this UI:** make the confidence score and its evidence trail the most legible thing on the screen, always. Everything else is chrome around that.

### 1.1 Role of Google Stitch
Google Stitch may be used as a design mockup and visual reference tool to explore component layouts and starting aesthetics for the Overview and Graph screens based on the design tokens and layout specifications in this document:
- Any design or code scaffolding produced by Stitch is strictly a **visual starting point**, not production code.
- Tokens defined in §2 and typography in §3 take precedence over any default values generated by Stitch.
- Reusable components (§6) must remain unified across the codebase rather than importing fragmented Stitch exports.

## 2. Color system

Dark theme. Background hierarchy communicates depth; accent colors carry meaning, not decoration.

```
--bg-base:        #0A0E14   (page background)
--bg-surface:      #10151D   (cards, panels)
--bg-surface-raised: #161C26 (hover states, active panels)
--border:          #232B38
--border-subtle:   #1A212C

--text-primary:    #E8ECF1
--text-secondary:  #8B95A5
--text-tertiary:   #5A6472

--accent-primary:  #3B82F6   (interactive elements, links, primary actions)
--accent-cyan:     #22D3EE   (graph highlights, active selection)

--score-weak:      #6B7280   ( < 0.30 — not actually reachable, no edge created below this, but reserved for UI use if ever shown )
--score-moderate:  #F59E0B   ( 0.30 – 0.59 )
--score-strong:    #3B82F6   ( 0.60 – 0.79 )
--score-very-strong: #10B981 ( >= 0.80 )

--evidence-supporting:   #10B981
--evidence-contradicting: #EF4444

--status-proposed:  #F59E0B
--status-confirmed:  #10B981
--status-rejected:   #6B7280  (muted, never deleted from view when relevant)
```

Score color bands must match `DATA_MODEL.md` §3 exactly: weak < 0.30, moderate 0.30–0.59, strong 0.60–0.79, very strong ≥ 0.80. Do not invent different thresholds for visual convenience.

**Supporting evidence is always green-family. Contradicting is always red-family.** This mapping is fixed and appears identically in the graph, the evidence panel, and any legend. A judge should learn it once and read it everywhere.

## 3. Typography

```
--font-display:  'Inter', -apple-system, sans-serif      (headings, nav)
--font-body:      'Inter', -apple-system, sans-serif       (body text, labels)
--font-mono:       'JetBrains Mono', 'Fira Code', monospace (handles, PGP fingerprints, wallet addresses, scores, any raw identifier)
```

**Rule: anything that is data, not prose, renders in monospace.** Handles, fingerprints, wallet strings, scores, timestamps, relay ids. This is not a style preference — it signals to the viewer "this is an exact value you could verify," which directly supports the provenance story `SECURITY.md` §3 is built around.

Scale: 12/14/16/20/28/36px. No more than these six sizes anywhere in the app.

```
├───────────┬─────────────────────────────────────────────┤
│           │                                             │

│  top      │                                             │
│  tabs     │                                             │
│  only)    │                                             │
│           │                                             │
└───────────┴─────────────────────────────────────────────┘
```

Top navigation, not a sidebar — reclaims horizontal width for the graph, which is the widest content on screen. Four tabs: **Overview · Graph · Dossier · Timeline**, matching the four Streamlit pages 1:1. No new screens invented.

Max content width: none. This is a data tool; use the full viewport, especially for the graph canvas.

## 5. Screens

### Overview
- Four stat cards in a row: Artifacts · Personas · Identifiers · Relationships. Large mono numerals, small label beneath
- Source health: three rows (forum-alpha, marketplace-beta, forum-gamma), status dot, last scan time
- "Run Correlation" button — primary accent, prominent, top right of this screen
- Below: a short list of the 2-3 highest-scored relationships as compact cards, each showing handle → handle, score with color band, one line of top evidence

### Graph
- Two-pane layout: canvas left (roughly 65%), evidence inspector right (roughly 35%) — mirrors the Streamlit layout in the reference screenshot, which was already structurally correct
- Nodes: circle, colored by `source_id` (three fixed colors, one per source, with a legend), label beneath in mono font showing the handle
- Edges: line thickness scales with score; color follows the score band from §2; `transacted_with` edges render as **dashed**, `same_actor_suspected` as **solid** — the type must be visually distinguishable before you even open the inspector
- Selected edge: highlighted in `--accent-cyan`, other edges dim to ~40% opacity
- Rejected relationships: render at very low opacity (~15%), never fully hidden — an analyst should be able to see that a link was considered and dismissed, not just that it's absent. This is a genuine intelligence-tool property worth keeping visible

### Evidence Inspector (right pane of Graph, always present when an edge is selected)
- Link header: `handle → handle`, relationship type as a small pill/badge
- Score: large, mono, colored by band, with the band label ("Strong Link" etc.) — never a percentage, see `SECURITY.md` §5
- Status pill: proposed / confirmed / rejected, colored per §2
- Confirm / Reject buttons — only enabled when status is `proposed`
- Evidence list: one row per signal. Each row: colored dot (supporting=green, contradicting=red), signal name in mono, weight with explicit sign (`+0.70`, `−0.30`), one-line human note, and a clickable reference to the source artifact
- **Nothing in this panel may be summarized or hidden.** Every evidence row from the API response renders. This is non-negotiable per `SECURITY.md` §4 — contradicting evidence is never suppressed

### Dossier
- Persona header: handle (large, mono), source badge, active window (first_seen → last_seen)
- Identifiers section: PGP fingerprint and wallet, each in a copyable mono block
- Linked personas: cards showing each relationship, score, and a link to jump to that edge in the Graph view
- Activity summary: post count, span

### Timeline
- Horizontal time axis, one lane per persona (6 lanes)
- Each persona's activity window as a bar from first_seen to last_seen
- **The `quillfeather` → `quill_v2` handoff must be visually obvious**: `quillfeather`'s bar ends, a short gap, `quill_v2`'s bar begins on a different lane. This is the single most important visual moment in this screen per `DEMO_SCRIPT.md` — do not let the timeline library's default rendering bury it in noise
- Hovering a bar shows the persona's full window and a link to its dossier

## 6. Reusable components

Build these once, use everywhere — do not let a UI generation tool produce four different score displays for four screens.

- `<ScoreBadge score={0.95} />` — mono number + color band + label, single source of truth for score rendering everywhere in the app
- `<StatusPill status="proposed" />`
- `<EvidenceRow signal={...} />`
- `<SourceBadge source="forum-alpha" />` — consistent color dot + label
- `<MonoValue>` — wrapper for any raw identifier (fingerprint, wallet, handle) ensuring consistent font and truncation-with-copy behavior

---

## 7. What not to build

- No light theme / theme toggle. Dark only
- No animation beyond simple hover/transition states (150-200ms). No particle effects, no elaborate graph physics beyond a standard force-directed layout
- No illustrations, no stock icons beyond a small functional icon set (lucide-react is fine)
- No marketing-style hero section on Overview. This is a tool, not a landing page
- No feature not present in the four Streamlit pages. This is a visual/interaction upgrade, not a scope expansion — `REQUIREMENTS.md` still governs what the system claims to do
